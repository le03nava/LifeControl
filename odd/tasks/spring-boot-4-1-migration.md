## Specs

S1 — **Destination and unification**: "el destino sería 4.1.1, unificar api y gateway a la misma version".
Both `life-control-api` and `api-gateway` end on Spring Boot **4.1.1**, the same version, in the same change.

S2 — **Jackson 3**: "migrar a jackson 3".
Native Jackson 3 (`tools.jackson`). The `spring-boot-jackson2` stop-gap module and `spring.jackson.use-jackson2-defaults` are **not** used, not even temporarily.

S3 — **Two steps**: "dos pasos".
Pinned interpretation: the two steps of the Boot 4.0 migration guide's "Migration Strategy" — an intermediate state with `spring-boot-starter-classic` / `spring-boot-starter-test-classic` where auto-configuration keeps working while imports and dependencies are fixed, then a second step that drops the classic starters and adopts the per-technology starters and package names. The four answers were given against the four open decisions of the previous turn in order (destination, unification, Jackson, strategy), and this is the fourth.

**L5** (2026-10-16, T2 implemented by `gentle-ai-worker`; the cache-format hypothesis in L4 is falsified):

- `./gradlew compileJava` on Boot 4.1.1 is **BUILD SUCCESSFUL** after three source fixes (verbatim before/after in the worker's evidence; the RED was the 2 errors + 2 `[removal]` warnings recorded in L4).
- `SecurityConfig`: the diagnostic was `Supplier<CAP#1> cannot be converted to Supplier<Authentication>`. Spring Security 7.1.1 declares `AuthorizationManager.authorize(Supplier<? extends Authentication>, T)` and 6.5.11's `check(...)` is gone, so the method-reference parameter was widened to `Supplier<? extends Authentication>`. Verified with `javap` against `spring-security-config-7.1.1.jar`. Body, rules, CSRF and the JWT wiring are textually unchanged.
- `ContentCachingFilter`: Spring Framework 7.0.9 has only `ContentCachingRequestWrapper(HttpServletRequest, int)`; `spring-web-6.2.19`'s removed 1-arg constructor stored `contentCacheLimit = null`, and 7.0.9 stores `null` for any argument `<= 0` with the same buffer capacity. `-1` behind a named `UNLIMITED_CONTENT_CACHE` is byte-equivalent; a positive limit was rejected because it would truncate the audit payload that the activity-log aspect replays.
- `CacheConfig`: **no remaining `DefaultTyping` constant works.** Measured against the real cached shape — `getAllCountries` returns `Stream.toList()`, i.e. `java.util.ImmutableCollections$ListN`, a **final JDK container class** — all six constants (`JAVA_LANG_OBJECT`, `OBJECT_AND_NON_CONCRETE`, `NON_CONCRETE_AND_ARRAYS`, `NON_FINAL`, `NON_FINAL_AND_ENUMS`, `NON_FINAL_AND_RECORDS`) write a bare payload and then fail on read with `SerializationException`: the writer gives a final container no type id while the reader, whose root is declared `Object`, demands one. Every `@Cacheable` read of the six cached regions would have been a 500. Spring Data Redis' own Jackson 3 helpers (`GenericJacksonJsonRedisSerializer.builder().enableDefaultTyping(...)`, `.enableUnsafeDefaultTyping()`, `RedisSerializer.json()`) produce the same unreadable payload. The fix is a 12-line `CacheValueTypeResolver extends DefaultTypeResolverBuilder` reproducing Jackson 2's `EVERYTHING` body.
- **Falsified premise**: the wire format is **byte-identical** to the Jackson 2 output and old entries read back equal. Measured out-of-tree against the real production `CacheConfig.valueSerializer()` and the real `CountryResponse`: `OLD_WIRE_IDENTICAL_TO_NEW=true`, `OLD_LIST_READ_BY_NEW_SERIALIZER_EQUALS=true`, `NEW_ROUNDTRIP_EQUALS=true`. An incompatible entry still raises `SerializationException` out of `RedisCache.deserializeCacheValue` → `CacheErrorHandler` → `SimpleCacheErrorHandler` (which rethrows), i.e. it errors for the entry's TTL rather than becoming a miss — pre-existing behaviour, unchanged by this migration, and unreachable for existing entries.
- `src/main` keeps no `com.fasterxml.jackson.databind|core` import; the single remaining `com.fasterxml.jackson.annotation.JsonTypeInfo` is `jackson-annotations` 2.21, which Jackson 3 still uses. `tools.jackson.core:jackson-databind:3.1.5` arrives through `spring-boot-starter-jackson` → `spring-boot-jackson:4.1.1`; `spring-data-redis` resolves to 4.1.1; `spring-boot-jackson2` is absent anywhere.
