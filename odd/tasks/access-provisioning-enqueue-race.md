**L1** — *2026-10-17, the user's request, verbatim*: *"continua con 4) Deudas declaradas de employee-access-provisioning — T15 diferido y los gaps acotados: race residual de G39, la decisión de acoplamiento G40 (T67), G42 y G43. **L2** — *2026-10-17, the measurement that classified the four, and the recommendations the user accepted.* Everything below was read against the code, not against the records' prose.

- **T15 is retired, not deferred.** `EmployeeService.resolveEmail` (`hr/service/EmployeeService.java:352-360`) throws when `company.emailDomain` is null or blank **even when the request carries an explicit address**, so the "domain cleared after the employees exist" shape is the only reachable one and the credential surface T104 deleted has nothing left to cover. No work.
- **G39's residual race is implementable, and this is the recommendation that was opened as a unit.** `AccessProvisioningProducer.enqueue` pre-checks with `findFirstByEmployeeIdAndStatusInOrderByRequestedAtDesc` and then calls `gateService.request(...)`, which reaches `AccessProvisioningTaskService.create` (`:158-183`) — and that method **pre-checks again** (`existsByEmployeeIdAndStatusIn`) and calls `save` **without a flush**. Two concurrent facts for one employee therefore both pass both pre-checks, and the partial unique index `uq_access_provisioning_tasks_open` refuses one **at commit**: `DataIntegrityViolationException` → `GlobalExceptionHandler:71` → **409**, with the whole HR write rolled back. The catch is correctly forbidden (a `RuntimeException` crossing a participating `@Transactional` boundary marks the transaction rollback-only, which `AccessProvisioningProducerTransactionIntegrationTest.theNaiveShapeCannotSwallowTheRefusal` proves), so what is missing is the **lock**, not a `try`. The race is reachable only from facts that do **not** write the employee row — a contract insert (`ContractService.createContract:203`) and a store-assignment write (`EmployeeStoreAssignmentService`) — because an employee-row write already serializes the two transactions on its own row lock.
- **G40 stays accepted, and its defect was already closed by another unit.** `AccessProvisioningGateService.request` is `@Transactional` and `deriveReviewedDiff` reads the account's client roles live (`currentRoles` → `IdentityProvider.getUserRoles`) inside that transaction, so an unusable admin client fails the HR write closed with **503** and rolls it back. The measured 500 — a `jakarta.ws.rs.ForbiddenException` escaping unmapped — was closed by the G11 unit (`1588261`, PR #347 → `3a19856`). The alternatives (create without the diff, or swallow the read) are the un-reviewed apply **T67** exists to forbid, and the "task born gated with no diff" shape is **not** free: `reenterGateIfReviewedSetChanged` returns `false` immediately when there are **no** frozen rows ("an untouched task pays nothing"), so an empty frozen set would skip the re-derivation entirely and would need a new state to be distinguishable from an auto-apply task.
- **G42 stays accepted.** The company-wide queue reads **only** `APPROVAL_PENDING` (`AccessProvisioningQueryService:227`, `findByEmployeeCompanyIdAndStatus`), by design (T94), and the requester's name falls back to the `sub` in the UI already (`access-requests-list.ts:66`, `access-review-dialog.ts:107`). The second limit has **no local name source at all** — the requester can be an operator who is not an employee of this application — so "closing" it means denormalising names into this database and keeping them fresh.
- **G43 stays accepted, for now.** Measured: `grep` over `life-control-api/src`, `docker/` and the scripts finds **no** DSN reader, no delivery-report handling and no Keycloak event listener. A Keycloak listener can only observe what Keycloak already knows at send time — which is the signal the application already has — while only a DSN reader (or a relay's webhook) observes the real bounce, and **which of those is right depends on the production relay**. The operator's `resend` (T69) is the retry meanwhile.

- **T2 GREEN, observed.** The same class plus the three classes that pin the shapes S3 protects — `AccessProvisioningProducerTest` (16 tests), `AccessProvisioningProducerTransactionIntegrationTest` (3), `AccessProvisioningTaskConcurrencyIntegrationTest` (3) — answer **23 tests / 0 failures**, `GRADLE_EXIT=0`, and `spotlessCheck` is clean. The guard is `EmployeeRepository.findByIdAndCompanyIdForUpdate` (`@Lock(PESSIMISTIC_WRITE)`), called at the top of `enqueue` **before** the open-set read.
- **The lock order was measured, not assumed.** `EmployeeService.updateEmployee` → employee row, then producer; `ContractService.createContract` → contract row, then producer; `EmployeeStoreAssignmentService.createAssignment`/`closeAssignment` → assignment row, then producer; `AccessProvisioningWorker.process` takes the task lock in `claim`'s own transaction and writes the employee row in a **separate** one, so it holds no task lock while writing the employee. Every writer is `employee → task`, and no path takes them inverted. That is what makes the guard deadlock-free rather than merely plausible.
- **The second door was found by that measurement, and it is the same defect.** `AccessProvisioningTaskService.create` has exactly one production caller (`AccessProvisioningGateService.java:148`), but `AccessProvisioningGateService.request` has **three**: `AccessProvisioningProducer.java:198` (guarded by T2) and `AccessProvisioningRequestService.java:100` (`apply`) and `:136` (`deactivate`), which take **no** employee-row lock. Two concurrent operator requests, or one racing a producer fact, therefore still pass both pre-checks and lose one write at commit with the same generic 409. The fix is the same guard one layer up, in `request`, which is the single door the other two call sites share — so **S3a** was added and **T2b** opened instead of declaring a half-guarded surface as done.
- **A deviation worth stating rather than hiding**: the new test lives in `…/provisioning/**service**/` and not directly under `…/provisioning/`, because `AccessProvisioningTaskService.OPEN_STATUSES` is package-private and S3 requires asserting against the landed definition of "open" instead of a second copy of it.
- **A property of the harness, stated as a property and not as a bug**: the losing thread's bounded wait expires (~5 s) when the winner takes the lock first, and the run still asserts the invariant — the lock serializes the commits either way. Observed runs were fast.

**L7** — *2026-10-17, the independent verification of the high-risk claim (Risk item 4), and the three findings it leaves standing.* `gentle-ai-verify` was asked to falsify five claims and returned **VERIFIED on all five, with no blocker**:

- **Each door carries its own regression proof.** Removing **only** the producer's lock makes the fact scenario fail **3/3** runs; removing **only** the gate's lock makes the operator scenario fail **3/3**, with the constraint violation that door used to produce. Neither guard is decorative.
- **The guard is what makes it pass.** The unmodified class ran **3/3 green** (31 s / 19 s / 26 s), and the true pre-fix bytes — both locked calls removed — went **8/8 RED**, each one `DataIntegrityViolationException` on `uq_access_provisioning_tasks_open`. The commit message's claim about the pre-fix failure is therefore reproduced by someone other than its author.
- **No test was weakened to make the change fit.** The two edited classes were read with `--word-diff`: no assertion was deleted or relaxed. A probe that moved the employee read above the company access check still failed `the company check is the first statement`, so the class has not gone blind to that ordering.
- **The lock order holds.** The only production call sites of the new finder are `AccessProvisioningProducer:178` and `AccessProvisioningGateService:152`; every writer reaches a task row through the producer after its own row write; `AccessProvisioningWorker` claims the task in a transaction of its own and touches the employee row in another; and no `readOnly = true` path reaches the lock, which PostgreSQL would refuse.
- **The producer's semantics are unchanged.** Same-kind suppression, different-kind supersede + create, and the naive catch's rollback-only failure are all still pinned and green (41 tests / 0 failures on the changed bytes).

The three findings it leaves, recorded rather than smoothed over: (1) **the race suite is a probabilistic invariant guard, not a proof that the race happened in each run** — the harness starts both threads on a `CyclicBarrier` and holds A's task uncommitted for a 300 ms grace, so a run in which one thread finished its entire transaction before the other began its producer call could pass with the guard absent; it never did in the 8 pre-fix runs, and the deterministic pin of `L8` is the answer to that residual; (2) `foreignOrUnknownEmployeeIsRefused` no longer distinguishes the guard by itself, because Mockito's default `Optional.empty()` satisfies it either way — the in-order verification in the same class is what carries that guarantee; (3) the base fact scenario spends ~5 s when A wins the employee lock, so the class runs 19–31 s instead of ~1 s. None is a merge blocker, and none was closed by weakening a claim.

**L8** — *2026-10-17, the durable probe the verification proposed, taken and committed as its own slice.* The verifier's report carried a ready probe — `theEmployeeRowIsLockedBeforeTheOpenSetRead` in `AccessProvisioningProducerTest`, an `inOrder` check that the employee row is locked **before** the open-set read — which it had validated on the committed bytes and confirmed fails with `WantedButNotInvoked` once the call is removed. It pins in milliseconds what the integration suite can only pin with real PostgreSQL and a latched interleaving.
