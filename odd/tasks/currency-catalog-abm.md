## Problem

The global `currency` catalog is seeded by `V57` and every company carries a `currency` that references it, but **nothing in the application can change a row**: `CurrencyController` has exactly one endpoint, `GET /api/currencies`, and its own javadoc states the absence is deliberate — «There is no `POST`/`PUT`/`DELETE` because there is no screen that edits a currency» (`currency/controller/CurrencyController.java:19-22`).

The consequence became concrete on 2026-11-09. `#830` (`1c531404`) taught `updateCompany` to keep a stored currency the catalog has since retired, so a company is no longer stranded by a retire. **That state cannot be produced.** `enabled = false` is reachable only by writing a migration, so the fix defends a state the product cannot enter, and no operator can retire a currency without shipping SQL.

Every other global catalog in this tree already has its write half: `payment_methods` has `POST`/`PUT`/`DELETE`/`PATCH /{id}/enable` (`PaymentMethodController.java:54-97`), and so do `measure_units` and `seniority_levels`. `currency` is the catalog that was left read-only because no screen asked for it — and a screen is how this repository has always decided it, not a reason to leave the API half-built.

## Specs

- **S1 — the write half, matching the precedent.** `POST /api/currencies`, `PUT /api/currencies/{code}`, `PATCH /api/currencies/{code}/enable` and `DELETE /api/currencies/{code}`, the four verbs `PaymentMethodController` already carries (`:54,:69,:96,:84`). `GET /api/currencies` keeps its mapping, its `includeDisabled` parameter and its `CurrencyResponse` record byte for byte.
- **S2 — authorization copies the existing answer, it does not invent one.** Every write is `@PreAuthorize("hasAnyRole('lc-admin','lc-currency')")` at method level, the shape `PaymentMethodController.java:55,70,85,97` uses; reads stay `isAuthenticated()`. `lc-currency` joins `Roles.java` beside `COUNTRY`, `PAYMENT_METHOD` and `MEASURE_UNIT`, is provisioned by `docker/scripts/keycloak-setup.sh` in the same list (`:490`), and is **absent from every `ScopeLevel`**, because a global catalog has no tenant in which to scope it (`ScopeLevel.java:34-36` states that rule). `/api/currencies` is already on `TenantScopeFilter`'s tenant-agnostic list (`:109-116`), so no path changes.
- **S3 — the code is the key, and the refusals are explicit.** A create with a code that already exists is **409**, never a silent overwrite; `minorUnits` outside `0..4`, a `symbol` longer than 6 characters, and a `code`/`minorUnits` that is null or not exactly three characters are **400** by bean validation, because the DDL already refuses them (`V57:60-65`) and a violation reaching the database would surface as a 500 on a request the API could have judged. **The code must match `[A-Z]{3}`**: the column is `CHAR(3)`, so `mxn` would be a second row for the same currency beside `MXN`, and `resolveCurrency` looks up exactly what it is given — a catalog with two spellings of one currency is the data defect this unit exists to prevent. The rule is a **refusal**, never a silent normalization: the caller's string is not rewritten. A `PUT` on a code that does not exist is **404**, and a `PUT` whose body states a **different** code than the path is **400**, because the column is the target of five foreign keys and a code is never renamed.
- **S4 — retiring is `PATCH /{code}/enable`, and `DELETE` is refused.** `companies.currency` (`V57:81-82`) plus four further FK columns (`variant_listing.currency`, `stock_movement`, `stock_valuation`, `sales_orders.currency`) point at the row, so a hard delete of a **referenced** code is refused by the database and surfaces as **409** through the existing `DataIntegrityViolationException` handler — never a 500. A delete of a code nothing references is **204**, and that success path is pinned too, because `currency` seeds only `MXN` and a fresh environment may hold no row pointing at whatever was created. **The limit is stated, not papered over**: the Java half of that chain (`GlobalExceptionHandler` mapping `DataIntegrityViolationException` to 409) is proven at the controller boundary, while Postgres raising `23503` and Hibernate translating it is framework behavior this unit does not own and does not test — the same boundary `payment_methods` has, which carries no integration test for its delete either.
- **S5 — the read cache must not survive a write.** `CurrencyService` is `@Cacheable(value = "currencies", key = "'all-' + #includeDisabled")` with **no eviction anywhere**, and its javadoc says that absence was intentional while nothing could change a row (`:14-19`). Every write evicts the region, and a test proves `GET /api/currencies` reflects a retire immediately instead of after the cache expires.
- **S6 — the state `#830` defends becomes reachable and stays safe.** After a currency is retired by the API, a `PUT` on a company whose stored currency is that code still succeeds with the value unchanged, and a change **to** that code is still 400. The two halves must be proven together, in this unit, because until now one of them could not happen.

**Deliberately out of scope**, and each for a stated reason: the Angular screen (no catalog-ABM screen exists to copy; needs a design pass and a menu-entry decision); company-level overrides of the catalog (the seam `product_attribute_profiles.company_id` has zero rows and is its own decision); the `tax_code` and attribute-profile catalogs (same shape, after this one sets the mould); and any change to `minor_units` semantics or to the `V57` DDL.

## Log

**L1 — the request.** The maintainer asked «cual recomiendas continuar?», was given the measured list of pending work, and chose «ABM de monedas — mi recomendación» (option `currency-abm`). The recommendation given, and the reason this unit exists in this order: the `#830` fix merged on 2026-11-09 defends a state the product cannot produce, so the ABM is what makes it reachable.

**L2 — the decision the exploration found rather than invented.** The question "who may edit a global catalog" is already answered three times in this tree — `hasAnyRole('lc-admin','lc-<catalog>')` at method level, the path on `TenantScopeFilter`'s tenant-agnostic list, the role absent from every `ScopeLevel`. `payment_methods`, `measure_units` and `seniority_levels` all follow it, and `/api/currencies` is already on that list. So T2 and T3 copy a decision instead of taking one.

**L3 — two traps the map exposed before any code.** `CurrencyService` caches the whole catalog with no eviction, and its javadoc records that as intentional because nothing could change a row; adding writes without eviction leaves `GET /api/currencies` serving a retired currency as enabled, which is the failure the ABM is supposed to fix. And `Currency` has no setters and no builder, so the write path needs the mutators the read path never did. Both are T1/T2 work, not surprises for the reviewer.

**L4 — the boundary of the slice.** The API is one reviewable unit; the screen is not in it. `odd/tasks/hr-org-structure.md:51` records that this repository's global catalogs have no menu entry at all, and `:60` (D14) excluded the catalog-admin roles from the grantable set. A screen is therefore a decision about the menu and the roles, not a rider on an endpoint slice.

**L5 — the independent verification, and what it changed.** `gentle-ai-verify` read the slice against S1–S6 and returned PASS on all six with no blocker, which is worth less than its four advisory findings. Two were accepted as work: the `PATCH …/enable` NPE that turned `{"enabled": null}` into a **500** (RED observed: `Status expected:<400> but was:<500>`), and two refusals that were construction-only at the HTTP boundary. One was refused as out of surface: `PaymentMethodController#setPaymentMethodEnabled` has the same unboxing defect, it is not this unit's file, and it is named in the currency controller's javadoc so the reviewer sees it was found rather than missed. One was deferred as pre-existing: the `@CacheEvict` after-invocation and the transaction share `LOWEST_PRECEDENCE`, so a concurrent read can re-cache a pre-commit list — the same shape exists in all four sibling services, it is reasoned rather than measured, and it is not introduced here.

**L6 — the verification caught a contradiction inside my own T6.** The row rewritten for `AGENTS.md:218` said the catalog no longer changes by migration while `AGENTS.md:215` still said «lectura pura: se siembra por migración y no hay ABM», and `life-control-api/AGENTS.md` was worse: a path table listing `/api/currencies` as «read-only … no write path», a role table and a role list without `lc-currency`, and a cache section explaining that the region needs no `@CacheEvict` because nothing can change a row. That is the same defect this session fixed twice already (#832) — a doc row asserting an absence that the tree no longer supports — and this time it was inside the unit that created the falsehood. Six spots across the two files, corrected in the docs commit.

**L7 — what the slice does not prove, stated so nobody reads it as proven.** The FK-to-409 chain is proven at the controller boundary with a stubbed `DataIntegrityViolationException`; Postgres raising `23503` and Hibernate translating it is framework behavior, and `payment_methods` carries no integration test for its delete either, so this unit matched the boundary that exists instead of inventing a wider one. The `[A-Z]{3}` rule is a guarantee about the API, not about `CurrencyService`: a direct caller could still pass a lowercase code, exactly as every sibling catalog allows, and no path in this tree creates a row except HTTP.

**L8 — the slice boundary, decided with the maintainer.** 1,523 authored lines across 15 files, against an advisory budget of ~400. The alternative offered was a chain of three pull requests; the maintainer chose one pull request read as three commits. The cut is by concern and not by file type, so no commit ships code it does not prove: `5ffee3a7` is the API and its authorization with the security suite (660 lines), `1c33d1f4` is every refusal, the eviction and the reachable retire with their cases (863 lines), and this docs commit is the two `AGENTS.md` files and this record. Splitting further would separate a refusal from the endpoint it refuses, which is the one cut that makes either half unreviewable.
