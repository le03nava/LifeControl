# store-location-chain

**Status**: implemented
A store is born stock-ready: `POST …/stores` now creates the location chain that `store_inventory_settings` requires, in the same transaction. Issue #859. Branch `feat/store-location-chain`, base `origin/main` @ `440879ec`.
Nothing is deferred: the two decisions the issue leaves open (the names, and whether receiving and sales share a location) are taken here and recorded as L3/L4.

## Specs

- **S1** — Issue #859 acceptance: "Creating a store leaves it able to accept `PUT /api/variants/{variantId}/stores/{companyStoreId}` with `{"stock": N}` and answer 200, without a manual configuration step."
- **S2** — The auto-created chain is exactly **one area, one zone and one location**, with codes and names stated in L3, and `store_inventory_settings` names that single location for both `receiving_location_id` and `sales_location_id`.
- **S3** — The chain is created inside `createStore`'s transaction, after the store's own insert and before the response: a failure rolls the store back, and because `KeycloakGroupEventListener` is `@TransactionalEventListener(AFTER_COMMIT)` no Keycloak group is created for a store that does not exist.
- **S4** — Everything that read the chain keeps working: `GET …/stores/{id}/store-locations` lists the one created location, the inventory-settings panel still reads and saves, and the store-delete cascade disables the chain it now finds (one area, one zone, one location).
- **S5** — Non-goals, quoted: "Does not name the auto-created area, zone or location, and does not decide whether receiving and sales share one location." "Does not change the ledger: `applyStockAdjustment` and `stock_position` stay the only writers and readers of the quantity." "Does not touch the search predicate; a variant with no per-store row should keep being excluded from a store-scoped search."
- **S6** — Consequence of S5 that the acceptance test must state rather than assume: the search predicate keys on **per-store** rows (`product_variant_store_stock`, `variant_listing`, `stock_position`), never on locations, so the chain alone makes no article visible. The article appears because the `PUT` of S1 writes the store's own stock row — measured at `ProductVariantRepository.java:296`.

## Log

- **L1** (user, verbatim): "has el merge de 858 y 859"
- **L2**: #858 and #859 are issues, not pull requests; after the #858 delivery the human chose the fork #859 names in its own acceptance criteria: *"Autocreate: la tienda nace stock-ready"* over a readiness marker.
- **L3** (decision: the names). Nothing in the tree had ever created a chain row — no migration seeds `store_areas`, `store_zones` or `store_locations`, no fixture name is canonical, and both the API and Angular forms start empty — so the names are this unit's to state: area `DEF` / "Default area", zone `DEF` / "Default zone", location `DEF` / "Default location". Codes are 3 characters against the column's `varchar(10)` and names are 13-16 against `varchar(100)`. The word **Default** is deliberate: an operator who later splits the store into real areas must be able to see at a glance which rows the server invented, and the code `DEF` is greppable in a dataset.
- **L4** (decision: sharing). Receiving and sales point at the **same** location. The schema allows it (`store_inventory_settings` has no check that the two differ) and sharing keeps a first store's inventory in one bucket instead of inventing a distinction the operator never made; splitting later is an ordinary settings save on a screen that already exists. The alternative — two locations of one zone — would have booked receipts and sales into two places a human had not decided.
- **L5**: Scope correction measured before writing code: the issue's third acceptance bullet ("the variant appears in `/api/product-variants/search` for that `storeId`") is **not** a property of the chain. `ProductVariantRepository.java:296` requires a `product_variant_store_stock`, `variant_listing` or `stock_position` row for that store, and locations appear in none of them. The chain makes the `PUT` of S1 succeed; the `PUT` writes the row that makes the article visible. The test asserts both halves so the causal chain is not mistaken for the trigger.
- **L6**: The chain is written by a dedicated collaborator rather than by calling `StoreAreaService`/`StoreZoneService`/`StoreLocationService` from `createStore`: those services resolve the store through their own access checks and enablement guards, and each is shaped for an operator request. The collaborator writes the four rows with the entities' own mappings and inherits nothing that assumes a caller. `CompanyStoreService` already injects `storeAreaService` for the delete cascade, so the dependency direction is unchanged.
- **L7**: A hazard the plan did not anticipate, and the reason the collaborator flushes per row — but **not** the one first written here. A first draft of this record and of the commit message claimed that `hibernate.order_inserts=true` sorts pending inserts by entity name, putting `StoreZone` after `StoreLocation`; the independent verification read hibernate-core 7.4 and **refuted it**: `ActionQueue.InsertActionSorter` builds a real foreign-key dependency graph from each insert's state and schedules groups out of a first-encounter-ordered map, so a plain `save` in tree order would already have produced area → zone → location. The real constraint is the schema's: `V59`'s `derive_store_zone_store_from_area` and `derive_store_location_store_from_zone` are `BEFORE INSERT` triggers that derive `company_store_id` by **selecting the parent row from the database**, so a parent still pending in the persistence context makes the trigger derive `NULL` into a `NOT NULL` column. `saveAndFlush` per row is what guarantees the parent is in the database when its child's trigger runs. Kept in the log because the wrong mechanism was load-bearing in the code's own javadoc and in this record, and a reviewer would have carried it forward.
- **L8**: Deliberate facts about the created rows: `display_order` and `description` are left `null` (the listings order by `display_order` then code and there is exactly one row per level, so stating an order would invent one), and `enabled(true)` is stated explicitly although the column defaults to it, so the enabled-only listings and the delete cascade both see the chain. The settings row is `saveAndFlush` as well, so no statement of this method can fail after the store's response is built.
- **L9**: Two behaviours left as they are, named here so a later reader does not mistake them for oversights. (a) **Store delete** now *removes* the `store_inventory_settings` row — this was first written here as an accepted leftover and the native review rejected it (see L12), so the sentence is history, not the current behaviour: the tree rows are disabled and kept as history, and the settings row is deleted because it is an address for new writes, not history. (b) **Re-enabling a store** does not re-enable or re-create the chain, because the cascade has no inverse. Both were reachable before this change only for a store whose chain an operator had built by hand; the change makes them the default path, so a follow-up that owns store lifecycle (enable/disable/delete) should decide them together. Neither is a regression this unit introduces, and neither is silently wrong: a disabled location is exactly what a disabled store's inventory should look like.
- **L11**: What the independent verification added beyond the correction in L7, and what was deliberately not taken. It proposed two **characterization tests** for L9 — `delete → re-enable` leaves the chain disabled, and a deleted store still answers `200` to a stock write booking into a disabled location. Both are honest and neither is here: a test that freezes today's answer for a hole nobody has decided is a policy choice disguised as coverage, and it belongs to the lifecycle slice that decides the answer, not to the unit that made the hole the default path. It also noted that the S6 pair proves "a per-store row is required" rather than "the search is scoped to that store" (the query token is unique, so a cross-store check would be the stronger test); the store-scoped read is already pinned by the store-scoped suites, and adding a second store to this fixture would prove the predicate twice.
- **L10**: Delivery strategy, recorded because the change is past the ~400-line review slice: **one PR with two commits** (155 production lines, then ~725 of tests and this record). The chain exists because 2071 lines could not be reviewed as one candidate (#858); 880 can, and the measured native-review budget on this repo is around a thousand lines per candidate, so splitting further would buy ceremony and not focus. The boundary is real either way: the first commit is the behaviour, the second is its proof.
- **L12**: The native review found, and a refuter confirmed, that **declaring a hole in L9 did not make it acceptable**. Both lenses raised the same CRITICAL finding (`R1-001`, `R3-001`, `causal_disposition: introduced`): persisting the `store_inventory_settings` row in the create path left the stock-write precondition in place after the store was soft-deleted, so a **deleted** store answered `200` to `{"stock": N}` and booked inventory into a disabled location — while at baseline a store created through `POST` had no settings row and the same write answered 404. "It was reachable before via a hand-built chain" was true and irrelevant: the change made it **the default path**, and a soft delete that still accepts inventory is the exact opposite of what a soft delete means. The bounded correction (55 diff lines, plan declared at 60) has `deleteStore` call a new `StoreLocationChainService.removeInventorySettings(storeId)`: find-then-delete the row, in the same transaction, right after the area cascade. The ledger is untouched (S5) and the tree rows stay disabled. The RED is the pair itself — the same write answered `200` with a stock body before the correction and `404` after — and the case asserts the "before" 200, so it cannot pass on a store that never had the row.
