# ODD feature: fiscal-deploy-wiring

**Repository**: LifeControl — `docker/` and `k8s/` (the deployment of a fiscal capability that is otherwise built)
**Branch**: `feat/fiscal-deploy-wiring`, cut from `origin/main @ 7d87c6e4`
**Status**: **implemented** — issue #930, the last mile of the fiscal capability: the port, the adapter, the sealing pipeline, the CSD reader and both endpoints existed and a real deployment could reach none of them, because no `FISCAL_*` key existed in `docker/` and the CSD had no path into the container. What it owes: nothing. The five non-secret keys are declared in `docker/.env.template` and mirrored by the compose defaults, the four credentials arrive as mounted files read by the entrypoint wrapper, and an operator's own values stay in the untracked `docker/.env.<env>` so the template remains the safe default every new environment is born from (`L2`, `L6`, `L7`). What it deliberately leaves: a key-management service, because the CSD is a file; a seal the PAC accepts, which needs a real CSD and is stated as a limit in `L19`(e) of `odd/tasks/cfdi-fiscal-document.md`; the cluster path, because no manifest deploys this API at all (`T5`); and one residual named rather than hidden — the template keeps the vendor's public testing *user*, so an environment born from it that is given a production endpoint without its own user is refused by the vendor at the first stamp, loud and before any document is written, but not caught by a gate the way the testing *host* is.
**Created**: 2026-11-16 · **Risk**: item 5 (delivery and environment: it changes the deploy path and the gates that guard a start) and, in the narrow sense of credential *delivery*, item 2 — the four fiscal credentials arrive as mounted files exactly as `smtp_password` does, so no privilege boundary moves and no key becomes an environment value.

## Objective

Make the fiscal provider switchable by declaration in the shipped stack: a deployment that invoices states it and mounts its CSD, a deployment that does not starts byte-for-byte as it does today, and the repository's own gates catch a misconfigured one before it starts.

## Specs

Quoted from issue #930's acceptance criteria, verbatim.

**S1** — The CSD arrives as a mounted file read by a wrapper in `docker/entrypoints/`, which exports the values `CsdProperties` expects. It is **never** a versioned value and never an environment key holding a key, which is this repository's own rule.

**S2** — Every `FISCAL_*` key the provider needs is declared in `docker/.env.template` **and** in the compose's `${VAR:-…}` default, each with a consumer or a default, and `env-defaults.test.sh` covers the new ones.

**S3** — `validate-env.sh <env>` reports a missing fiscal setting without failing the dev start, and refuses it where the repository already refuses — the shape the SMTP and `frontendUrl` gates use.

**S4** — The provider stays **off** by default: `app.fiscal.provider.enabled` is false unless the deployment says otherwise, so a stack without a CSD boots and answers the named 503.

**S5** — An environment file that still points at the public testing host in staging or prod is refused, mirroring the fail-closed pattern the invitation flow already uses for `SMTP_HOST` and `KEYCLOAK_URL`.

**S6** — `k8s/manifests` carries the same settings for the cluster path, or the record states why it does not.

**S7** — The docker suites stay green: `image-pins`, `env-defaults`, `env-report-robustness`, `app-credential-split`, and the glob that runs them all.

**The residual, named instead of fixed.** The template keeps `FISCAL_SF_USUARIO=testing@solucionfactible.com`, the vendor's public testing account, so a new environment is born with it. **L5 (2026-11-16) — the two hand-written passwords were read byte-exactly, and a CR is what actually reached the vendor.** `fiscal_sf_password` and `fiscal_csd_password` are the only two of the four credentials with no `setup-env.sh` template behind them: an operator writes the file, so its last byte is whatever their tool wrote. The wrapper read them with `cat` while the certificate and the key two lines above already went through `tr -d '\r\n'`, so the two paths disagreed about the same kind of file. One correction is worth stating precisely, because it is not the one the defect report assumed: a trailing **LF** never leaked, since `$(cat …)` strips trailing newlines on its own — a *file saved on Windows* is the shape that leaked, because the CR survives command substitution and the vendor's authentication error names neither the file nor the byte. Both passwords now go through `tr -d '\r\n'`, and the assertion that fails on the old code is the CRLF one; the newline and no-terminator cases pass before and after, so they are pinned as behaviour that must not regress rather than as a repair.

**Why the tolerance stops at those two files.** `DATABASE_PASSWORD`, `FLYWAY_PASSWORD` and `KEYCLOAK_ADMIN_CLIENT_SECRET` are materialized by `setup-env.sh` from tracked templates, so their bytes are decided by a file in this repository and are not an operator's accident. Relaxing them here would decide a different unit's question inside this one, and the wrapper's comment now says so where the change is.

**The shape `$(cat … | tr -d '\r\n')` rather than the certificate's `tr -d '\r\n' <file`.** `app-credential-split.test.sh:220` reads the literal token `$(cat ` on every `*PASSWORD` export line as its evidence that the value came from a mounted file and never from a literal, and that suite is not this task's to edit; the certificate and the key stay in redirection form because their variable names are not `*PASSWORD` and no such loop sees them. The pipe keeps both facts true.
