# ODD feature: retire-legacy-realm-roles

**Repository**: LifeControl — `life-control-api/` (`common/security/Roles.java`, `common/auth/CurrentUserContext.java`) and their tests, `docker/scripts/keycloak-setup.sh` plus its offline suites, `README.md`, `life-control-api/AGENTS.md`. Issue #682.
**Status**: implemented — both legacy realm roles are out of the accepted authority set, out of the provisioning script and out of the documentation, and the two realm roles are deleted from the **dev** realm. What remains outside this slice is the same deletion in the **staging and prod** realms, which this repository's tooling cannot reach: it is written out as the operator step in T8 and is the only outstanding item.
**Created**: 2026-10-29 · **Risk**: item 2 (security) — the diff edits the authority set the API accepts, and `isAdmin()` short-circuits all five `verifyCompany*Access` checks, so a mistake here is a permission error rather than a visible defect. It was routed accordingly: the removal is pinned by a test that fails if the legacy authority is accepted again, the provisioning side by a suite case that fails if the name returns, and the diff went to an independent `gentle-ai-verify` pass. Item 3 does not apply — the removed authority was requested, and no consumer inside the repository used it.

## Specs

S1 — **"no hay ningun usuario legacy con esos roles en ningun ambiente"**.
The premise that makes the removal non-breaking: no realm has a holder of `life-control-admin` or `life-control-country`, so retiring both deletes no one's access. The claim is measured, not assumed: the dev realm answered 0 members for both roles on 2026-10-29 (L3), and the Admin API queries that produced it are the reproducible check named in T6.

S2 — **"Sí: issue + worktree + la slice completa"**.
One issue, one worktree, one slice carrying **both** roles — not a split between the zero-risk one and the dangerous one. The option's own description is the scope: issue first (the repository requires it before code), the worktree through `new-unit.sh`, the ODD record, and the two roles in a single pull request.

S3 — **"el más peligroso: quitarlos deja en 403 a cualquiera del realm que todavía tenga el rol viejo y no los lc-*"**.
The hazard the removal has to survive, quoted from the request that opened the review. "Quitarlos" means all four surfaces a role lives on, and all four are in scope: the code that accepts it, the script that provisions it, the realm record that holds it, and the documentation that declares it accepted. Retiring the code alone would leave the role re-creatable on every run of `keycloak-setup.sh`.
