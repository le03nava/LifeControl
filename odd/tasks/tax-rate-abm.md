# tax-rate-abm

**Status**: implemented
A tenant-scoped ABM over `tax_rate`, the table ADR-0002 decision 6 resolves from and that until now had **no writer in any layer**. Issue #858. Branch `feat/tax-rate-abm`, base `origin/main` @ `440879ec`.
Nothing is deferred: the rate a company declares through this resource is the one `TaxRateService.resolve` answers for a document dated on or after its `effective_from`.

## Specs

- **S1** — "`POST`/`PUT` over a tax-rate resource creates and supersedes a rate for `(company, tax_code, effective_from)`, and the row it writes is the one `TaxRateService.resolve` answers afterwards for a document dated on or after that `effective_from`."
- **S2** — "the rule that a rate change appends a new `effective_from` row instead of rewriting the old one is enforced where it is written, not only by `uq_tax_rate_company_code_from`."
- **S3** — "A rate that would duplicate an existing `(company, tax_code, effective_from)` answers 409 and writes nothing; a `rate` outside `[0, 1]` answers 400 and writes nothing."
- **S4** — "A caller without the role answers 403, and a rate of another company is a 404 — the same answer an inexistent one gives."
- **S5** — "After declaring `IVA` at 16% with an `effective_from` before the document date, a sale of a product declaring `IVA` is accepted and its line carries `tax_rate = 0.160000`; before declaring it, the same sale is still refused with the current message."
- **S6** — "The existing reads keep working unchanged: `/api/tax-codes` still serves the catalog, `TaxCodeService.isZeroRateByDefinition` still short-circuits `NA`, `TASA_0`, `EXENTO`, and `./gradlew test` passes."
- **S7** — The write guard is `lc-tax`, the convention's **one write role per catalog** (`Roles.java:34`). It is a functional role like `lc-employee`: deliberately absent from every `ScopeLevel`, with the company scope verified from the `{companyId}` path. The role is added to the `keycloak-setup.sh` provisioning loop in the same commit, because a role the realm never creates is a role nobody can hold.
- **S8** — Non-goals, quoted from the issue: "Does not change the resolution rule (`latest effective_from <= document date`) or the refusal in `SalesOrderService`/`PurchaseOrderService`." "Does not solve #855: one rate per code per date remains one rate until that is decided separately." "No decision here on whether a company gets a default rate at creation."

## Log

- **L1** (user, verbatim): "has el merge de 858 y 859"
- **L2**: #858 and #859 are **issues**, not pull requests — there was nothing to merge (verified: `gh pr list --search "858 OR 859"` returns only two unrelated merged PRs, and no branch names either number). The human then chose, explicitly: *"Aprobar #858 y #859 y empezar a implementarlos"*. `status:approved` was applied to both issues; this record owns #858 and `odd/tasks/store-location-chain.md` owns #859.
- **L3**: Decision — the write guard is a **new** `lc-tax` role rather than `lc-admin` alone. Evidence: `Roles.java` documents the convention as "one write role per catalog", and the eight catalog ABMs in this tree each carry one. `lc-tax` follows `lc-employee`'s shape (functional role, absent from `ScopeLevel`, scope verified from the path claim) because a tax rate is company-scoped data while its write authority is functional, not a tenancy level.
- **L4**: Decision — **`rate` is never rewritten.** `TaxRate` maps `id`, `company_id`, `tax_code` and `effective_from` as `updatable = false`, and the ADR's own words are that history *is* the audit. Therefore `POST` appends, `PUT /{id}` appends the successor of the row it names, and the only column a write mutates in place is `enabled`. This is S2 enforced in the service: the forbidden rewrite is not expressible.
- **L5**: Decision — `PUT /{id}` requires `effectiveFrom` **strictly after** the row it supersedes. "Supersede" that could also append into the past is not a supersede, and a caller wanting a historical backfill has `POST` for exactly that.
- **L6**: RED observed before any production code existed: `TaxRateControllerHttpIntegrationTest` 11 cases, **10 failed**, every one `Status expected:<201|403|400> but was:<404>`. The eleventh — `unknownTaxCodeIsNotFound`, which expects a 404 — passed **vacuously**, because a route that does not exist also answers 404. That is the trap the supplier suite's own javadoc names, so it was strengthened rather than left alone: it now asserts the error body **names the code**, which no missing route can produce. The three 404s of `anotherCompanysRateIsNotFound` got the same treatment (body names the rate id) after the run, with the "row untouched" assertions kept.
- **L7**: A real defect the tests found, not a test expectation: `TaxRate.declare` stored `0.16` where the column is `NUMERIC(9,6)`, so the POST/PUT response and any resolution answered before the persistence context was cleared carried `0.16` while the row and every later reader carried `0.160000`. In a tree where a line **snapshots** that value and `ck_item_tax` compares it against the stored rate, a response that disagrees with the row is the exact class of bug ADR-0002 decision 6 exists to prevent. Fixed at `TaxRate.declare`: the rate is stated at the column's own scale (`RATE_SCALE = 6`, `RoundingMode.HALF_UP`, the same rounding PostgreSQL applies).
- **L8**: The **first full-suite run failed on the new acceptance suite only** (2 of 2), while both cases passed alone — measured proof that "green in isolation" is not green. Two order-dependence defects in the fixture, both in `TaxRateSaleAcceptanceTest` and neither in production code: (a) the refusal case asserted `sales_order_items` and `sales_orders` counts **table-wide**, and a previously committed suite's rows made them non-zero — scoped now to this suite's own company+store and its own variant, so the property asserted is "this refused sale stored nothing" rather than "the database is empty"; (b) the teardown deleted `shifts` while `sales_orders` still referenced it, and `shifts` carries no tenant policy (`V53` does not arm it), so an unscoped `deleteAll()` reached **another suite's** shift. The teardown is now dependency-ordered and company-scoped throughout, reusing the base class's `deleteSalePayments` and `deleteStockLedger`. The RED was reproduced deliberately with JUnit's class order forced (`-Djunit.jupiter.testclass.order.default=…ClassName`, process env only): 82 tests / 2 failed before, 82 / 0 after. Worth keeping: a suite that needs a forced class order to fail is a defect the default order was hiding, not a test that was fine.

The boundaries are the ones in the table above: the writer (475), the resource that exposes it (581), the proof that the two halves close the loop the issue describes (~640). - **L11**: One defect the author introduced and reverted, kept in the record because the check is the lesson: `TaxCodeNotFoundException` **already existed** for this exact fact (`ProductService:403` asks the catalog and throws it), and overwriting the file changed its message from "Tax code not found with code: X" to a new sentence. No test pins that string, so the full suite could not catch it — the diff did. The file is back at `HEAD` byte for byte and the new service reuses the class unchanged. **A class that already exists for the reason you need is not a class to rewrite.**
- **L12**: The independent verification found a **blocker in the new code**, and it was right. An explicit `"enabled": null` was turned into `true` by both request records, so a caller who stated the field with no value got a rate that starts applying to documents — and `PATCH …/enable` with the same body raised an NPE through `getOrDefault` and answered **500**. The tree had already fixed that exact defect on that exact endpoint shape: `CurrencyController#enabledFlag` refuses a present null with a 400 and says why ("answering the first with the default would mean this endpoint silently turned 'no value' into 'enable it', which is the one direction an operator never means when they send the field"), and `companies.currency` has no default for the same reason. Fix: `enabled` is **required** on both write records (`@NotNull`), so absent and stated-null are both a 400 naming the field, and `PATCH` reads the body through a helper that copies the currency logic — absent key is the only default left, and it is `true`. This is S3 tightened: a refusal now also covers a flag the caller failed to state, in the direction that changes what a document is charged.
- **L13**: The same verification named a gap in S7 that nothing would have caught: **no test tied the `Roles` constants to the `keycloak-setup.sh` provisioning loop**. Measured: 28 `lc-*` constants and 28 roles in the loop agreed exactly, so the link held — and a forgotten line would have made `lc-tax` ungrantable with every gate green, which is the failure mode of this whole unit one level up. `KeycloakRoleProvisioningCoverageTest` now pins both directions, recomputing both sides from the files, and the proof that it bites is a mutation: `lc-tax` commented out of the loop turned it red naming the role, and the script was restored byte-identical (`sha256` and `git diff` both reported).
- **L14**: Two limitations accepted rather than fixed, both named by the verification. (a) The **database still grants** `UPDATE`/`DELETE` on `tax_rate` (`V82:133-136`, "nothing is granted and nothing is revoked"), so append-only holds inside the entity but not against a raw writer; tightening it is a migration of its own with the `REVOKE` shape `V60`/`V67` use, and it is not this unit. (b) `requireCatalogCode` uses `existsById` and therefore admits a **retired** `tax_code`, which is what the product writer (`ProductService:403`) also does — consistent with the only existing writer of that column, and a rule about retired codes belongs in the catalog, not in one of its readers.
- **L15**: The verification's correction was **folded into the slice it belongs to** rather than left as a fourth "fix" commit: each fixup targeted the slice that owns the file, `--autosquash` reordered them, and the rebase was accepted only because the branch's total content was unchanged (`18 files changed, 2071 insertions(+), 12 deletions(-)` before and after). A chain whose last commit is "and also the thing the reviewer would have blocked" teaches the next reader that the review caught what the tests did not; a chain where each slice is already correct does not.
